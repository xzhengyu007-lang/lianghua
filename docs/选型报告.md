## 0. 一句话结论

**不引入任何平台型框架。** 只引入 **1 个前端运行时资产**（`lightweight-charts`，Apache-2.0，198 KB 单文件）+ **3 处设计借鉴**（vnpy_riskmanager 的规则清单、vnpy 的订单状态机、QIFI 的账户事件流）+ **3 处公式借鉴**（qlib 的横截面归一、arch 的 GARCH 口径、quantstats 的尾部指标）。

服务端**保留标准库 `ThreadingHTTPServer`**，不引入 FastAPI、不引入 Vite/Node/TS 构建。OMS / 风控 / 幂等 / 审计 / 对账**自建 300–600 行**（`quant_system/trading/`），理由见 §6。

这条结论的依据不是"框架太重"，而是三件实测事：**本仓只有 8 只票、月轮动、7 个依赖**；四类平台（截面 ML / RL / 深度时序 / SOTA 复现）与真正的瓶颈（检出力 56% 是统计功效问题）**正交**；而"要不要引入构建链"的答案是"官方产物已经给了，不必自建"。

## 4. 推荐 3 个主干参考

三条线各一个，**都只取"某一部分"**，不整体引入。

### 主干① tradingview/lightweight-charts（Apache-2.0，17815★）—— UI 中栏主图

- **拿哪一部分**：standalone IIFE 构建（198 KB）+ `CandlestickSeries` + `HistogramSeries`（成交量独立 pane）+ `timeScale().setVisibleLogicalRange()`。
- **贴到哪个文件**：`ui/vendor/lightweight-charts.standalone.production.js`（带 Apache NOTICE）、`ui/desk.js`、`ui/desk.html`；`scripts/serve_dashboard.py` 补静态路由。
- **为什么是它**：唯一同时满足「Apache-2.0」「单文件 `<script>` 即用」「canvas + 只画可视区间（10 万根不构成瓶颈）」三条的候选；`ghostfolio/Highcharts` 已被许可否决，`KLineChart` v10 的静默空白坑更贵。
- **代价与风险**：vendor 198 KB + 约 150–250 行 JS；**无内置指标与标记 API**（信号点标注要自己写约 60 行）；5.x API 与旧教程不兼容；"Lightweight Charts™" 是商标，不得用作本项目品牌。

### 主干② vnpy 生态（MIT，46276★ + 24★）—— 风控规则与订单状态

- **拿哪一部分**：
  1. `vnpy_riskmanager` 的**规则清单本身**（`duplicate_order_rule` / `daily_limit_rule` / `order_size_rule` / `active_order_rule` / `order_validity_rule`）与 `check_allowed(req) -> bool` 的插件协议 —— 这就是本项目红线清单的现成枚举；
  2. `vnpy/trader/constant.py` 的 `Status` 六态机（SUBMITTING/NOTTRADED/PARTTRADED/ALLTRADED/CANCELLED/REJECTED）与 `OrderRequest→OrderData→TradeData` 三段式（成交驱动账本）。
- **贴到哪个文件**：新建 `quant_system/trading/risk_rules.py`、`quant_system/trading/order_state.py`；`quant_system/paper.py` 的 `Ledger` 升 v2（加 `orders`/`audit` 段、`plan_orders` 出参加 `order_id`）。
- **为什么是它**：许可 MIT 可拷；12 KB 就覆盖了红线 1/2/4/5；六态机正好补 `paper.py` 目前"只有 fills、没有订单状态"的缺口。
- **代价与风险**：**不能拷文件**（import 了 GUI 主引擎），只能按清单重写；两条必须改进：`duplicate_order_rule` 的内存计数换成**落盘唯一键 `(trade_date, symbol, side)`**；`daily_limit_rule` 的本日计数要按 `trade_date` **显式跨日复位**（上游没有证明它会复位）。

### 主干③ nautechsystems/nautilus_trader 的对账设计（LGPL-3.0，31370★）—— **只读**

- **拿哪一部分**：`crates/execution/src/reconciliation/{mod,types,ids}.rs` 的差异分类与 in-flight 订单状态推断算法（下单后状态未知时如何判定差异归属）。

## 6. 三个需要你拍板的技术决策

### D1 服务端：保留 `ThreadingHTTPServer`（推荐）还是换 FastAPI

| | 保留 stdlib（推荐） | 换 FastAPI |
|---|---|---|
| 新增依赖 | **0** | starlette + pydantic + uvicorn（+ 传递） |
| 现有代码 | `serve_dashboard.py` 340–392 行的 `/api/run` 模式继续用，补 80–120 行路由 | 重写 `do_GET` 全部路由，静态文件仍要自己挂 |
| 收益 | 与「依赖极克制」「Windows 可装」一致 | 类型化端点、WebSocket 推送（3 s 行情可推而非轮询） |
| 风险 | 自己 gzip（一行 `gzip.compress`）、无 keep-alive 调优 | 三栏本地单用户场景下，这些收益买不回来 |

**推荐：保留 stdlib。** 与任务书默认（FastAPI）不同，理由是实测 `gh api` + 读码：本仓服务端已能跑 `/api/meta /api/run /api/rebuild`，缺的只是**静态路由**（20 行），不值得为它引入一条 Web 依赖链。若你要求 FastAPI，我照办，但要接受 3 个新依赖。

### D2 前端：无 Node（推荐）还是 Vite + TS

**推荐：无 Node。** 依据 §7 实测：两个 K 线库的官方产物都是单文件 `<script>` 即用，10 万根缩放帧 3.8–3.9 ms；引入 Vite 需要 Node + pnpm + 打包器 + 产物入仓的 CI 约定，**换来的产物官方已经提供**。代价：没有 TS 类型检查与模块打包（用 ES modules + JSDoc 顶替）。

### D3 L3 默认关闭 + 前置条件

**推荐：L3 默认关闭**，需显式开关 + 逐日授权；开启前置条件写死为「硬限额 + 熔断 + kill switch + 审计日志 + 小资金跑满 20 个交易日无事故」。`easytrader` 类"模拟点击"方案**不采用**（实测该仓库已被监管清空，见 §1.3）。

## 7. 10 万根 K 线可行性（本机实测）

| 库 | 产物形式 | 装载 100k | 平均帧 | 最大帧 | >20 ms 帧 |
|---|---|---:|---:|---:|---:|
| lightweight-charts 5.2.1 | 单 IIFE `.js`，`<script>` 即用 | 177.5 ms | **3.9 ms** | 8.2 ms | 0 |
| KLineChart 10.1.0 | 单 UMD `.js`，`<script>` 即用 | ≈176 ms | 3.8 ms | 4.0 ms | 0 |
| echarts 6.1.0（candlestick+dataZoom） | `dist/echarts.min.js`（仓库内自带） | 119.6 ms | 9.2 ms | 26.8 ms | 1 |

- **真瓶颈是数据搬运，不是渲染**：100k 根紧凑 JSON = 8.33 MB，gzip 后 1.06 MB。所以**不能**沿用 `build_dashboard.py` 的"数据全内嵌单文件"路线（0.9 MB 已接近舒适上限），必须走 `/api/bars?symbol=&from=&to=` 服务端切片 + gzip（本仓已有 pyarrow，也可直吐列存）。
- 本仓规模对照：`data/cache/*_raw.parquet` 共 269 个、单票 1800 行 → 全库约 48 万根日线。"10 万根"≈ 55 只票的日线合计，是真实场景。
- **口径声明**：上表是本机 Chromium 实测（rAF 未按 16.7 ms 节流，故帧时间≈单帧渲染成本），**跨机需重测**；测量脚本在仓库外临时目录，未入库。
